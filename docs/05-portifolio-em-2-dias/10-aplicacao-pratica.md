# Aplicação Prática para Desenvolvedores

Toda a teoria até agora é ótima, mas **como você realmente aplica isso em um portfólio de desenvolvedor**?

Esta é a ponte entre Design e Desenvolvimento.

---

## O Diferencial

Um portfólio de desenvolvedor geralmente mostra:

```
GitHub → Código → Screenshot
```

Mas você vai mostrar:

```
Problema → Solução → Processo → Resultado → GitHub
```

Essa é uma diferença enorme.

---

## Fluxo Ideal para um Projeto

### 1. Você tem um projeto (ou vai fazer um)

**Exemplo:** Um app Flutter de lista de tarefas.

### 2. Em vez de ir direto para o código, pense assim:

```
"Como vou APRESENTAR isso no meu portfólio?"
```

### 3. Estruture a narrativa

**Passo 1:** Qual problema isso resolve?

> "Usuários lutam para priorizar tarefas porque interfaces genéricas não comunicam urgência."

**Passo 2:** Como você resolveu?

> "Através de hierarquia visual: tamanho, cor e posição comunicam prioridade."

**Passo 3:** Quais decisões técnicas você tomou?

> "Escolhi Flutter porque X, BLoC porque Y, Supabase porque Z."

**Passo 4:** Quais foram os desafios?

> "Sincronização em tempo real foi o maior desafio. Resolvi implementando listeners."

**Passo 5:** Qual é o resultado?

> "Um app intuitivo onde usuários entendem prioridades em segundos."

---

## Como Estruturar a Página do Projeto

### Layout Recomendado

Uma página bem estruturada deve ter:

1. **Capa** — Nome do projeto + mockup principal
2. **Problema** — O que precisava resolver
3. **Solução** — Como você resolveu
4. **Processo** — Pesquisa, rascunhos, wireframes
5. **Decisões** — Por que essas escolhas de design e tech
6. **Resultado** — Screenshots/mockups finais
7. **Tecnologias** — Stack utilizado
8. **Links** — GitHub, Play Store, Demo

---

## Implementação Prática

### Opção 1: Website Próprio (Recomendado)

Crie um website pessoal (Docusaurus como você faz, ou Next.js/React) que:

- Tenha uma página por projeto
- Siga a estrutura acima
- Use imagens/mockups
- Tenha links para GitHub/demos

### Opção 2: Behance

O Behance é perfeito porque:

- Permite apresentar de forma visual
- Comunidade grande
- Fácil de compartilhar
- Recrutadores usam para procurar

### Opção 3: GitHub + README

Mesmo usando GitHub, melhore o README com seções para problema, solução, screenshots e aprendizados.

## Exemplo Real: Para Você (Desenvolvedor Flutter)

Suponha que você tem um **app de gerenciamento de projetos em Flutter**.

### Como Apresentar no Portfólio

**Seção 1: Problema**

"Gerentes de projeto usam múltiplas ferramentas (planilhas, WhatsApp, email). Resultado: dispersão, falta de visão única, retrabalho."

**Seção 2: Solução**

"Um app unificado onde projetos são centralizados, tarefas têm deadlines com notificações, comunicação em tempo real, e documentos anexados."

**Seção 3: Processo**

- Pesquisa: Entrevistei 10 gerentes de projeto
- Wireframes: Testei 3 estruturas de navegação
- Design: Paleta de cores para status (verde, amarelo, vermelho)

**Seção 4: Decisões Técnicas**

- Por que Flutter? Preciso cross-platform com performance nativa
- Por que BLoC? Preciso gerenciar estado complexo
- Por que Supabase? Preciso de sync em tempo real

## Checklist

Para cada projeto, pergunte-se:

- [ ] Consigo explicar o problema que resolve?
- [ ] Consigo explicar por que minha solução é melhor?
- [ ] Consigo explicar minhas decisões técnicas?
- [ ] Tenho screenshots/mockups profissionais?
- [ ] Tenho um link funcional (GitHub, app, demo)?
- [ ] Alguém consegue entender o projeto em 2 minutos?

Se todos forem "sim", você tem um projeto de portfólio profissional.

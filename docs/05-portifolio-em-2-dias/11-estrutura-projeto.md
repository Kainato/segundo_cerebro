# Estrutura Ideal de Um Projeto

Agora que você entendeu os conceitos, como estruturar **realmente** um projeto no seu portfólio?

A aula (através da proposta oficial da EBAC) deixa claro que o objetivo é transformar a prática em **projetos apresentáveis**.

Portanto, aqui está uma estrutura que funciona:

---

## Estrutura Recomendada

### 01 — Capa/Apresentação

**O que coloca:**

- Nome do projeto
- Uma frase curta explicando o que é
- Imagem principal/hero (mockup ou screenshot)

**Por quê:** Primeira impressão. O visitante sabe imediatamente o que é o projeto.

---

### 02 — Contexto

**O que coloca:**

- Quem é você (breve)
- Em qual contexto fez o projeto
- Por que decidiu fazê-lo

**Exemplo:**

> "Desenvolvedor Flutter com foco em experiência do usuário. Este projeto nasceu de uma necessidade pessoal durante estudos em um workshop."

**Por quê:** Mostra que você não faz projetos aleatoriamente. Há um propósito.

---

### 03 — Problema

**O que coloca:**

- Qual problema precisava ser resolvido?
- Por que era importante resolver?
- Contexto do problema

**Exemplo:**

> "Usuários de aplicativos de tarefas recebem feedback sobre dificuldade em priorizar atividades. A interface atual é genérica e não oferece pistas visuais claras sobre urgência."

**Por quê:** Recrutadores querem ver que você **entende o problema antes de codificar**.

---

### 04 — Objetivo

**O que coloca:**

- O que você queria alcançar?
- Como mediria sucesso?
- Qual era a meta?

**Exemplo:**

> "Criar uma interface intuitiva onde a hierarquia visual comunica prioridade sem precisar de textos explicativos. Usuários novos deveriam conseguir usar o app em segundos."

**Por quê:** Deixa claro que você define objetivos. Não é só "fazer algo bonitinho".

---

### 05 — Processo

**O que coloca:**

Mostre:

- **Pesquisa:** Como você entendeu o problema?
- **Referências:** O que você estudou?
- **Rascunhos:** Quais ideias explorou?
- **Wireframes:** Como organizou a informação?
- **Alternativas:** Quais soluções testou?
- **Iterações:** Como refinei a solução?

**Por quê:** Diferencia você de quem apenas copia templates. Mostra que você **pensa**.

---

### 06 — Decisões de Design

**O que coloca:**

Explique:

- **Cores:** Por que escolheu essa paleta?
- **Tipografia:** Por que essa fonte funciona?
- **Layout:** Por que essa organização?
- **Hierarquia:** Como guia o usuário?
- **Componentes:** Por que reutilizáveis?
- **Arquitetura:** Como estruturou o projeto?
- **UX:** Como o usuário flui?

**Exemplo:**

> "Utilizei uma paleta de 3 cores: azul primário para ações, verde para sucesso, vermelho para alertas. Isso comunica estado sem sobrecarregar. A hierarquia visual usa tamanho + cor."

**Por quê:** Mostra que suas decisões são **intencionais**, não acidentais.

---

### 07 — Resultado Final

**O que coloca:**

- Screenshots/mockups das principais telas
- Fluxo do usuário (como ele navega)
- Diferentes estados (idle, loading, error, success)
- Animações/interações importantes

**Por quê:** Agora o visitante vê o resultado. Mas já entendeu o **por quê** chegou lá.

---

### 08 — Tecnologias

**O que coloca:**

```
Frontend:
- Flutter 3.x
- Dart
- BLoC Pattern
- GetIt (DI)

Backend:
- REST API
- Node.js
- MongoDB

Infraestrutura:
- Firebase (Auth, Storage)
- Supabase (Database)
- Git
```

**Por quê:** Mostra a stack. Recrutadores veem se você domina as tecnologias certas.

---

### 09 — Aprendizados

**O que coloca:**

- O que você aprendeu fazendo o projeto?
- Quais foram os desafios?
- Como você os resolveu?
- O que faria diferente?

**Exemplo:**

> "Aprendi que BLoC é excelente para gerenciar estado complexo. O maior desafio foi sincronização em tempo real. Se fizesse novamente, usaria um state management menos verboso."

**Por quê:** Mostra humildade e crescimento. Recrutadores gostam disso.

---

### 10 — Resultado Final (Links)

**O que coloca:**

```
Vínculos:
[GitHub] — Código-fonte
[Play Store] — Baixar app
[YouTube] — Vídeo demonstrando
[Figma] — Arquivos de design
```

**Por quê:** Facilita o visitante explorar mais se interessado.

## Checklist

Antes de publicar seu projeto, verifique:

- [ ] Tem capa clara?
- [ ] Contexto é entendível?
- [ ] Problema está bem explicado?
- [ ] Objetivo é claro?
- [ ] Processo mostra pensamento?
- [ ] Decisões têm explicação?
- [ ] Resultado é visualmente atraente?
- [ ] Tecnologias estão listadas?
- [ ] Aprendizados são genuínos?
- [ ] Links funcionam?

Se a maioria for "sim", seu projeto está pronto.

---

## Dica Final

Essa estrutura não é rígida.

O importante é que seu projeto **conte uma história**:

```
Problema → Pesquisa → Ideias → Decisões → Resultado
```

Essa narrativa é muito mais poderosa que simplesmente listar features.
